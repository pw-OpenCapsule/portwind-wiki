# Wiki 结构：7 父节点定义

按**沉淀动机**分（不按主题），保证每个节点回答一个明确的「我现在有这个想沉淀，该放哪？」

## 7 个父节点

| 顺序 | 节点 | 定位 | template |
|---|---|---|---|
| 1 | 🛠️ **Skill 沉淀** | 团队自研 CLI / 插件 / agent skill — **怎么用** | [tool-self](templates/tool-self.md) |
| 2 | 📦 **产品沉淀** | 自研 SaaS / 部署型产品 | [product](templates/product.md) |
| 3 | 📐 **架构 & 调研** | design doc / 选型 / RFC — **为什么这么设计** | [design-doc](templates/design-doc.md) |
| 4 | 🩹 **踩坑 & 复盘** | `[坑]` gotcha · `[复盘]` 线上故障 RCA | [pitfall](templates/pitfall.md) / [postmortem](templates/postmortem.md) |
| 5 | 🚀 **团队入门** | 新人第一周：环境 / 账号 / 脚手架（**不含业务知识**） | [onboarding](templates/onboarding.md) |
| 6 | 📌 **工具雷达** | 团队发现的**外部**工具（不是自研） | [tool-radar](templates/tool-radar.md) |
| 7 | 🎤 **技术分享** | 历史分享归档 + 待分享 backlog | [share-talk](templates/share-talk.md) |

## 路由规则（解决边界争议）

| 内容 | 去哪 | 原则 |
|---|---|---|
| 「这个工具是干嘛的、怎么用」 | Skill 沉淀（自研）/ 工具雷达（外部） | **谁做的** |
| 「为什么选 X 不选 Y」 | 架构 & 调研 | **是什么 vs 为什么** |
| 个人撞过的小坑 | 踩坑 & 复盘 → `[坑]` | **轻** |
| 线上事故复盘 | 踩坑 & 复盘 → `[复盘]` | **重** |
| 新人怎么上手 | 团队入门 | **第一周看的** |
| Talk / slides / 录屏 | 技术分享 | **可分享性** |

## 每个父节点的索引页结构

索引页有 4 段必备内容：

1. **callout 定位** —— 一句话说本节点放什么 + 跟兄弟节点的边界
2. **当前内容表格** —— 子节点 / 工具 / 版本 / 状态等汇总
3. **写新条目的约定 / 模板** —— 链 templates/ 对应文件
4. **治理 / 维护说明** —— 怎么自清、归档规则

## 不建的节点（明确边界）

- ❌ 会议纪要 → 飞书妙记自动生成
- ❌ 个人学习笔记 → 私人空间
- ❌ 业务知识 → 太宽容易变垃圾桶；具体业务模块走 design doc 在架构 & 调研里写
- ❌ 「奇思妙想 backlog」 → 跟踪用 Linear / GitHub Issues 更好

## Homepage 导航表

Wiki 空间的根 Homepage 需要一个 7 行的导航表：

| 分类 | 放什么 | 最适合的提问 |
|---|---|---|
| Skill 沉淀 | ... | 「这工具怎么用？」 |
| 产品沉淀 | ... | 「这产品跑在哪？」 |
| 架构 & 调研 | ... | 「当初为什么选 X？」 |
| 踩坑 & 复盘 | ... | 「这错我见过吗？」 |
| 团队入门 | ... | 「第一周做啥？」 |
| 工具雷达 | ... | 「有人推过解决 X 的工具吗？」 |
| 技术分享 | ... | 「最近有什么分享？」 |

第三列「最适合的提问」是关键：让人自然语言搜索时秒命中。
